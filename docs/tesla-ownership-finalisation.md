# Pure confirmed-SMART ownership finalisation

This layer has no production caller, persistence, journal mutation, network or execution. The existing ownership store, supervised executor and reconciliation consumer are unchanged.

`ConfirmedSmartReceipt` binds the original `observedSmart` proposal and canonical payload, its exact approval, the prior ownership snapshot/generation captured during preparation, recognised accepted API result, authenticated exact read-back and classified journal bindings. It is trusted local evidence, not a browser contract. Its journal keys describe attestations a future durable-journal reader must supply; hashes cannot prove authenticity or disk durability. No such production issuer is implemented here.

`finaliseConfirmedSmartOwnership` checks the original proposal by recomputing it from its frozen original inputs, never from newer Kraken state and never as an `observedReplacement`. It reuses the existing read-back comparison, strict timestamp checks, proposal validator and timing constants. It returns a detached deeply frozen transition/evidence candidate, exact original proposal/payload keys, receipt identity, captured expected generation and retained blockers. Rejection returns only a safe structured code. There is no store commit, approval to execute, automatic recovery or claim of rollback proof.

`deriveOwnershipTransition` is the shared pure interval kernel. It accepts explicit authorised import-price segments, observed before/after states, comparison domain and prior ownership. A future replacement adapter can supply replacement scope directly; the existing replacement recording path is deliberately not connected in this change. The kernel itself is not sufficient confirmation evidence.

Economic comparison uses the existing observed-tariff analyser and common-domain validator. Segments split at before/after, authorised and prior-owned boundaries. Price amount, currency and unit compare exactly. SMART finalisation supplies only the originally selected absolute interval. New changed segments restore to the immediate before price; equal unowned segments remain unowned. Existing segments retain original restoration value and baseline fingerprint, and portions restored to that value retire. Other still-relevant owned portions must have coverage and remain consistent. Export and unauthorised import changes reject.

Still relevant means ending after submission; elapsed unowned prefixes cannot acquire ownership retrospectively. Existing historical prefixes may remain as history outside an advancing domain, but current/future omissions reject. Retained ownership validity is never extended. Absolute instants, including explicit DST offsets, bound ownership: recurring season representation does not create ownership on later dates. Existing simulation restrictions and production blockers remain intact, including `ROLLBACK_UNPROVEN` and bounded-forecast/restoration requirements.

Future store integration must check the captured generation inside its existing serialization boundary. Equal economics is not mutation identity; the receipt key includes exact mutation identity, original evidence and classified execution. This change does not implement already-recorded detection, crash recovery or production receipt issuance. A future failure after confirmed Tesla mutation must be reported separately as “tariff confirmed; ownership recording failed”, without retrying the write or resetting the latch. Journal durability and ambiguous filesystem completion still require separate integration/recovery design.

The lifecycle policies intentionally differ from existing `recordConfirmed`: the pure SMART transition uses submission time for still-relevant ownership, whereas replacement recording uses recording time for domain completeness; the pure transition retains elapsed owned history, whereas replacement recording can omit elapsed history outside its comparison domain; pure finalisation caps validity by inherited validity, whereas replacement recording assigns the new comparison-domain end; and SMART finalisation owns only the selected dispatch, whereas replacement recording uses replacement managed scope. These paths are not interchangeable. An explicit adapter/policy decision is required before any shared persistence connection.
