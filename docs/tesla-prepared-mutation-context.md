# Stage A: immutable prepared mutation context

`prepareMutationContext` is an isolated original-operation builder. The local B1 journal preparation port now consumes it. Its injected `readOwnership` port can use the existing store's read API; the builder itself installs no default filesystem/network adapter. The Stage A builder does not change approvals, execution sequence, latch, TTLs, blockers or ownership persistence. B1 adds the linked journal schema separately.

The builder detaches its site/selection/Tesla/Kraken inputs before awaiting anything. It reads ownership once, clones and validates the result, timestamps and deeply freezes it, and then prepares the original experiment using the existing preparation function. An available ledger retains its exact generation, evidence and checksum, including an empty interval list. Missing means the trusted read adapter reported absence; invalid, unavailable, corrupt or incompatible state never becomes absence. Existing ownership assertion checks the original Tesla before-state, timezone, chronology, validity and remaining owned economics.

Only after successful preparation/compatibility checking does the injected ID generator run once. The concrete string must meet the existing finaliser's ID format. A future local adapter can supply randomUUID. Fresh revalidation must keep this context and use the existing prepareSupervisedExperiment; it must not call the original-operation builder again. This helper does not provide replay protection or authenticate caller-supplied data.

The versioned, detached, deeply frozen PreparedMutationContext retains the complete original review and captured ownership, explicit site/timezone, selected dispatch, comparison domain, original wider SMART and selected evidence keys, exact unchanged proposal/payload/experiment identities, and SHA-256 context/ownership identities using existing canonicalisation. Other visible dispatches remain evidence and cannot expand selected scope. Hashes prove consistency only, not authenticity or journal durability.

Later stages must separately bind this context into approval/journal records, issue trusted completion evidence, invoke the pure finaliser and perform a generation-checked ownership commit. Only journal identity/linkage is now connected by B1; completion capability, receipt issuance, finalisation and persistence remain disconnected. No receipt, generation substitution/rebase, ownership write or freshness renewal is implemented. The existing SMART/replacement lifecycle policy differences still require explicit resolution before shared persistence.

Successful Stage A preparation does not guarantee finalisation coverage. Matching ownership tomorrow can be valid and bound here while lying outside the selected day's comparison domain; the finaliser then rejects with OWNERSHIP_DOMAIN_INCOMPLETE. The executor now preflights the shared finaliser containment rule after fresh validation and before journal claim: every owned interval ending after submission must have its still-relevant portion [max(start, submission), end) covered by the comparison domain. This must neither rebase the captured snapshot nor broaden the selected dispatch. Stage A itself remains preparation only; see tesla-ownership-domain-preflight.md for the execution gate.

Valid repeated IDs are intentionally accepted here; uniqueness/replay enforcement belongs to durable journal/latch policy, not global Stage A state. Checksums/fingerprints do not establish authenticity or current store generation. Revalidation's obligation to retain the original context remains with a future caller. Cross-layer tests construct mock receipts only, without durable receipt issuance, live execution or persistence.
