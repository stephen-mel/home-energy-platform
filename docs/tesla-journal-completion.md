# Stage B2: trusted journal completion

`claimExperimentJournal(...).finish(classified)` now returns an opaque, frozen `JournalCompletionCapability`. Only `supervised-journal.ts` can register it in its module-private WeakMap. No mint/registration primitive is exported. The TypeScript brand is not authority: fabricated objects, copies and JSON round-trips have no registry membership. A different module instance or restarted process has no access to the original runtime authority.

Registry lookup, registration and freezing functions are captured during trusted module initialization, so later replacement of those functions cannot fabricate membership or substitute minted evidence. This is not a sandbox for a runtime already compromised before module initialization.

The narrow `journalCompletionForRecords(capability, initial, classified)` boundary returns immutable evidence only for a genuine capability and the exact validated B1 records. Evidence contains `completionSchemaVersion: 1`, `journalSchemaVersion: 1`, `energySiteId`, `mutationId`, `initialRecordId`, `classifiedRecordId` and the classified record's existing `completedAt`. It contains no proposal, payload, credentials or duplicated execution evidence. Hashes and valid records alone cannot create runtime authority.

Minting occurs after classified validation, append-open, write, file sync and successful close, preserving the existing filesystem sequence. Initial exclusive creation, write, file sync, directory sync/close and initial file close remain unchanged. No extra filesystem timestamp or durability operation is introduced. Failure can leave partial or complete bytes on disk; failure never establishes absence. The site latch remains consumed, without reset, retry or automatic reopening for another attempt.

The executor carries `journalCompletion` alongside its existing recorded result. This proves only that this journal implementation's required completion lifecycle succeeded. Rejected, unknown, transformed or insufficient-readback results can all receive completion authority; none is promoted to successful Tesla mutation, ownership eligibility, billing qualification or rollback safety. Existing write-ready and rollback flags remain false.

Capabilities are immutable, reusable and specific to one linked outcome. Validation is side-effect free: reuse must never cause an external action. Repeated processing must converge on the same evidence identity; future receipt issuance must converge on the same receipt or rejection. There is no consumed flag. This does not make `finish` reusable: its existing one-attempt guard remains unchanged.

No receipt issuer, finaliser, ownership persistence, recovery reader or ownership-domain preflight is connected. A crash after durable completion but before capability delivery leaves valid bytes and a consumed latch, but no recoverable runtime capability after restart. Future evidence-only recovery needs a separately reviewed trusted reader. The existing `OWNERSHIP_DOMAIN_INCOMPLETE` case still requires the future pre-write gate; Stage A preparation and B1/B2 linkage do not establish that owned intervals fit the selected comparison domain.

Tests use the existing filesystem import boundary with small controlled wrappers around temporary-file handles. They cover initial write/file-sync/directory-sync/close failures and classified append-open/write/sync/close failures, including delayed close. These are deterministic failure simulations, not proof against OS crashes, storage-device faults or filesystem durability guarantees beyond the existing successful sync/close contract.
